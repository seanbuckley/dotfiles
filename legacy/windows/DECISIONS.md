# Architectural Decisions: UI Standardization & Robustness

To ensure the `dotfiles-windows` repository remains portable, modern, and visually consistent, the following decisions have been implemented:

## 1. Centralized UI Helpers (`UI-Helpers.ps1`)

- **Decision**: All scripts that provide visual feedback should use a standardized set of UI functions (`Write-Header`, `Write-TaskStart`, `Write-Success`, etc.).
- **Why**: Ensures consistency in CLI output (icons, colors, and formatting). This makes the tools feel more professional and provides clearer feedback during long-running tasks.

## 2. Dynamic Path Discovery

- **Decision**: All scripts should eliminate hardcoded paths (e.g., `C:\Users\<name>\...`) in favor of dynamic discovery via `$PSScriptRoot`, `$PSCommandPath`, and `$env:USERPROFILE`.
- **Why**: This allows the repository to be cloned to any location (even on different drives) without breaking internal script references.

## 3. Safer Backup Logic

- **Decision**: Profile backups and other maintenance tasks should use dynamic environment variables (like `$env:OneDrive`) and provide safe fallbacks (like `$HOME\Documents`) if specific services are not available.
- **Why**: Prevents script failures on systems with different OneDrive configurations or no cloud storage.

## 4. Master Planning Document (`MASTER_PLAN.md`)

- **Decision**: Maintain a high-level roadmap to track the project's evolution across phases (Robustness, UI, Performance, Tooling).
- **Why**: Keeps the project focused and ensures that future contributions align with the overall vision (KISS, portability, visual polish).

## 5. No Machine-Specific Defaults in Source-Controlled Templates

- **Decision**: Templates committed to the repository must remain neutral. Runtime scripts may populate host-specific values after discovery, but the source-controlled baseline must not include usernames, OneDrive tenant names, or fixed install roots.
- **Why**: Prevents fresh installs, audits, and code review from inheriting false assumptions from one machine.

## 6. Validate Automation with `pwsh -NoProfile`

- **Decision**: Non-interactive validation should run with `pwsh -NoProfile` and scripts must tolerate redirected or non-VT output.
- **Why**: Dotfiles code is used both interactively and by tooling. A profile that only works in a rich terminal is not robust enough.

## 7. Repo-Owned Chocolatey Backups

- **Decision**: Package-manager backups should be generated by repo-owned PowerShell and saved under each discovered backup root, including OneDrive and Dropbox when available, instead of relying on package-owned config files or third-party backup scripts.
- **Why**: The upstream `choco-package-list-backup` project is unmaintained, assumes brittle output formats, and spreads behavior across package-owned paths outside this repo. A repo-owned backup path is easier to reason about, validate, and keep portable.

## 8. Keep WSL Updates Separate from System Upgrade

- **Decision**: `Update-System` should not check for WSL sudo readiness, prompt for WSL credentials, or run WSL internal updates. WSL maintenance belongs behind the explicit `upgradeWSL` command.
- **Why**: The primary `upgrade` command should stay focused on Windows and package-manager maintenance without cross-environment password prompts. WSL updates can require Linux sudo behavior that is better handled intentionally as its own task.

## 9. Local Package Block Lists for Fragile Upgrades

- **Decision**: Windows package-manager steps may consult a local `DotfilesUpgradeSettings` map for package exclusions, instead of hardcoding host- or app-specific exceptions in tracked files.
- **Why**: Some Winget or Chocolatey packages are too fragile for a fully unattended run on every machine. Local block lists let one host skip known-problem packages without weakening unattended updates for everything else.

## 10. Separate Manual Follow-Up from the Main Summary

- **Decision**: `Update-System` should emit a dedicated follow-up section for skipped or failed package-manager items after the full run summary.
- **Why**: End users should be able to let the unattended run finish, then immediately see only the exceptions that still need human attention.

## 11. Install Profile Loaders for Both Windows PowerShell and PowerShell 7

- **Decision**: `Install-Dotfiles.ps1` should create or update thin loader profiles in both `Documents\WindowsPowerShell` and `Documents\PowerShell`, regardless of which host launched the installer.
- **Why**: Fresh-machine setup often starts in Windows PowerShell but day-to-day usage may happen in PowerShell 7. Wiring only the invoking host leaves the other shell family unconfigured, which makes aliases, prompt styling, and helper functions appear to "disappear" after restart.

## 12. Capture Reinstall-Oriented Chocolatey Metadata

- **Decision**: The Chocolatey backup flow should save a reinstall-friendly `packages.config`, a pinned-package export when available, and a plain-text installed-programs inventory.
- **Why**: The old third-party tool aimed to preserve enough state to rebuild a machine after failure. We do not need all of its cloud-target permutations, but we do want the same practical recovery outcomes from code we own.

## 13. Keep Profile Startup Focused on Interactive Essentials

- **Decision**: `Microsoft.PowerShell_profile.ps1` should eagerly load only the commands needed for an interactive shell session, while maintenance scripts are registered lazily and dot-sourced on first use. Generated init code from tools like `zoxide` and `oh-my-posh` should be cached under local app data and reused until the underlying executable or config changes.
- **Why**: Shell startup happens constantly, while commands such as `backupAll`, `upgrade`, and profile-copy helpers are occasional tasks. Deferring those scripts and caching generated prompt/navigation init keeps startup responsive without changing the public command surface or introducing machine-specific paths into the repo.

## 14. Expensive Profile Niceties Should Be Opt-In

- **Decision**: High-cost interactive extras such as `Winget CommandNotFound`, `git-aliases`, and `Terminal-Icons` should default to off in the shared profile and be enabled explicitly through environment variables or local profile overrides when a host benefits from them.
- **Why**: Startup timing showed these features consuming a meaningful share of every new shell launch. They are useful, but they are not as fundamental as prompt, editing, or navigation, so the portable default should favor responsiveness and let each machine opt back into the extras it values.

## 15. Treat Profile Load Time as a Guardrail

- **Decision**: Future changes to `Microsoft.PowerShell_profile.ps1` and related startup hooks should consider profile load time part of the feature budget. When profile behavior changes, capture startup timing before and after so regressions are visible instead of accidental.
- **Why**: Small convenience changes can quietly add hundreds of milliseconds each, which compounds into a noticeably sluggish terminal. Keeping timing visible makes it easier for future humans and agents to preserve features without drifting back into multi-second startup delays.

## 16. Standardized Output for Bulk Operations (e.g., `glall`)

- **Decision**: Scripts performing bulk operations across multiple targets must provide a clear "TaskStart" marker, a single success/fail indicator per target, and display any relevant command feedback (errors or meaningful logs) on indented new lines. Each target's output block should be separated by a newline.
- **Why**: Prevents UI clutter where output from a command (like `git pull`) blends into the next repository's status line. This ensures errors are clearly associated with the correct target and improves readability during high-volume operations.

## 17. Handle Specific Package Manager Non-Errors as Notes

- **Decision**: Specific exit codes like Winget's `0x8A150004` (metadata mismatch) should be caught and recorded as a "Note" rather than an "Error".
- **Why**: Some apps with internal auto-updaters (e.g., Chrome, Discord) frequently cause Winget to report metadata mismatches even if the app is current. Treating these as errors creates "false alarm" fatigue; treating them as notes keeps the report accurate without signaling a failure.

## 18. Refresh Winget Sources Before Enumerating Upgrades

- **Decision**: `Update-System` should run `winget source update` before listing or applying Winget upgrades.
- **Why**: Winget upgrade decisions depend on source metadata. Refreshing sources first reduces stale package lists while keeping source-update failures visible in the normal upgrade summary.

## 19. Resolve the oh-my-posh Themes Directory Instead of Trusting `POSH_THEMES_PATH`

- **Decision**: The profile should locate the oh-my-posh themes directory itself — preferring `POSH_THEMES_PATH` when it points at a real directory, then probing the layouts used by winget, scoop, and Chocolatey installs — and fall back to the built-in default theme with a startup warning when no theme file is found.
- **Decision (follow-up)**: A copy of `powerlevel10k_rainbow.omp.json` lives in `PowerShell/Themes/` and is used whenever the installed oh-my-posh does not ship the theme on disk.
- **Why**: `POSH_THEMES_PATH` is published by the installer, so it disappears after an uninstall and only reappears in sessions started after the reinstall. Depending on it made a routine version upgrade break the prompt with `Cannot bind argument to parameter 'Path' because it is null`. Some install methods (packaged/Store builds especially) never write a themes folder at all, so probing the disk is not enough either - keeping our own copy of the one theme this repo actually uses makes the prompt identical on every machine regardless of how oh-my-posh was installed.

## 20. Restore From a Shared Winget List, Keep Chocolatey as a Fallback

- **Decision**: `Restore-Winget` installs `Packages/winget-shared.json` first, then the host's newest winget backup when one exists. The shared list holds only apps every machine should have; host-specific apps stay in each host's backup. Chocolatey stays installed and backed up, and is restored separately from its `packages.config` for packages winget lacks or handles badly.
- **Why**: A rebuilt machine has a backup to restore, but a new machine has none, so restore used to do nothing there. A tracked shared list gives every machine the same baseline. It was seeded from the packages winget-installed on all four Windows hosts (2026-10 exports), leaving out runtimes and apps Windows already ships, then adjusted on review: VS Code only (VSCodium is a per-machine choice), NanaZip instead of 7-Zip, and Firefox (en-CA) added alongside Chrome. Chocolatey still covers packages winget handles badly, matching D5 in the merge plan. The list moves into `packages.yaml` at P4.04.
